Commenting Policy

Use comments to preserve design intent, not to narrate Python.

Add Comments For

  1. Invariants that future edits must preserve.
  2. Why a surprising branch, estimate, or synchronization exists.
  3. Ownership boundaries between scheduler, engine, attention, and cache code.
  4. Device or kernel constraints that are not obvious from types.
  5. Performance tradeoffs where the simple implementation would be wrong.

Do Not Add Comments For

  1. Restating a function or variable name.
  2. Explaining normal Python syntax.
  3. Long tutorial material inside production code.
  4. Comments that duplicate tests or drift-prone implementation details.
  5. Speculation that is not enforced by code or tests.

Preferred Shape

# Cached prefix entries are already valid in the page table.
# Allocate only pages intersecting [cached_len, device_len).

Two short lines explaining the invariant are usually better than a paragraph explaining the whole serving system.

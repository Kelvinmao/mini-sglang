Can Mini-SGLang Run on Mac Mini?

Goal: understand why the current repo is not Mac-ready, and what a realistic Apple Silicon adaptation would look like.

Short Answer

No, not as the current server. This repo is written around Linux, NVIDIA CUDA, CUDA graph replay, FlashInfer/SGL kernels, and NCCL-style GPU communication.

A Mac Mini adaptation is possible as an educational single-device backend, but it would be a port. It should first preserve the scheduler/KV-cache ideas and give up the CUDA-specific performance features.

Why A Simple Install Will Fail

  1. The README says Mini-SGLang is Linux-only and depends on CUDA-specific packages.
  2. engine.py hardcodes torch.device("cuda:{rank}"), CUDA streams, CUDA events, and CUDA memory checks.
  3. Attention, sampling, activation, norm, RoPE, KV-store, and tensor parallel communication paths call CUDA-oriented packages or custom CUDA/Triton kernels.
  4. The Dockerfile is based on NVIDIA CUDA images, which do not make Apple Silicon GPUs available as CUDA devices.

The Key Distinction

Run current Mini-SGLang

Needs a Linux + NVIDIA CUDA environment. Use a remote GPU box, a Linux desktop/server, or cloud GPU.

Run the ideas on Mac

Keep tokenizer, API shape, scheduler, request lifecycle, and KV-cache data model. Replace CUDA execution with a simple PyTorch CPU/MPS backend.

Recommended Mac Port Scope

Do not try to port the whole performance stack first. Start with a deliberately slower backend:

  1. Single Mac device only: --tp-size 1.
  2. No CUDA graph capture.
  3. No FlashInfer, TensorRT-LLM, or SGL CUDA attention backend.
  4. No PyNCCL/NCCL.
  5. Use torch.device("mps") if available, otherwise CPU.
  6. Use PyTorch attention and PyTorch tensor indexing for KV-cache storage.

Porting Plan

  1. Add a device selector in engine config: auto, cuda, mps, cpu.
  2. Split CUDA stream/event/memory behavior behind a runtime abstraction. On MPS/CPU, use synchronous behavior first.
  3. Add a torch attention backend that uses ordinary PyTorch matmul/softmax or scaled-dot-product attention.
  4. Add a PyTorch KV-cache store implementation to replace store_cache on non-CUDA devices.
  5. Replace FlashInfer sampling with PyTorch softmax, topk, multinomial, and argmax fallbacks.
  6. Replace FlashInfer activation/norm/RoPE calls with PyTorch implementations or already-existing model-layer logic.
  7. Make CUDA dependencies optional so macOS can install the educational backend without FlashInfer/sgl-kernel.
  8. Run only small models and short contexts first.

What You Should Not Port First

Do not begin with tensor parallelism, CUDA graph equivalents, fused Metal kernels, or performance parity. Those are second-stage projects. The first win is getting one request through the lifecycle on a Mac, even if it is slow.

Retrieval Check 1

If you adapt Mini-SGLang for a Mac Mini, what should you preserve first: scheduler/KV-cache semantics or CUDA graph performance?

Preserve scheduler/KV-cache semantics first. CUDA graph performance is a CUDA-specific optimization and should be removed from the first Mac backend.

Retrieval Check 2

Which file is the biggest early blocker because it hardcodes CUDA device, stream, event, and memory behavior?

python/minisgl/engine/engine.py. It assumes CUDA during engine initialization and forward result handling.

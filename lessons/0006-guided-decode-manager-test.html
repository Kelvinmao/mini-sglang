Guided DecodeManager Test

Goal: make one real miniature contribution: focused tests for scheduler decode-policy invariants.

The Win

This lesson turns the previous workflow into a concrete repo change: tests/core/test_decode_manager.py. It tests DecodeManager without launching a model server.

Primary sources: scheduler/decode.py, core.py, and the decode-manager test pattern.

The Change

We added a test file for existing behavior. No production scheduler code needed to change because the current implementation already satisfies these invariants.

  1. An empty manager is not runnable and schedules no batch.
  2. Decode batches are sorted by request id.
  3. Finished requests are filtered out.
  4. Remove and abort discard running requests.
  5. inflight_tokens includes remaining decode tokens plus page slack.

Why This Is The Right Seam

DecodeManager only manages a set of scheduler-side Req objects. It does not need model weights, tokenization, attention kernels, CUDA graphs, or ZMQ. That makes it an ideal first policy seam.

A small seam is valuable when it lets you test the exact invariant that would otherwise be hidden inside a full server run.

The Test Helper

The test creates real Req objects because DecodeManager depends on Req.can_decode and Req.remain_len. It stubs only the cache handle because decode policy does not inspect cache contents. 

class DummyCacheHandle(BaseCacheHandle):
    def get_matched_indices(self):
        return torch.empty(0, dtype=torch.int32)

That is the testing rule: use real objects for the fields whose behavior matters, and stub only the dependency that is irrelevant to the invariant.

The Important Invariant

The most scheduler-relevant test is stable ordering: 

manager.filter_reqs([make_req(3), make_req(1), make_req(2)])
batch = manager.schedule_next_batch()
assert [req.uid for req in batch.reqs] == [1, 2, 3]

The implementation uses a set for running_reqs, so sorting in schedule_next_batch is what makes the batch order deterministic.

Finished Requests

A request becomes unable to decode when remain_len reaches zero. The test uses Req.complete_one() to simulate the engine advancing a request after one forward pass. 

finished_req = make_req(2, output_len=1)
finished_req.complete_one()
manager.filter_reqs([finished_req])
assert finished_req not in manager.running_reqs

How To Run It

Once the Python environment is installed, run: 

python -m pytest tests/core/test_decode_manager.py -q

If the local pytest plugins are not installed yet, disable configured addopts while you bring up the runtime environment: 

python -m pytest -q -o addopts='' tests/core/test_decode_manager.py

For dated local verification blockers, see NOTES.md.

Retrieval Check 1

Why does the test use real Req objects instead of plain dictionaries?

Because DecodeManager relies on Req.can_decode and Req.remain_len. Plain dictionaries would not test the real request-length behavior.

Retrieval Check 2

Why does schedule_next_batch sort requests even though running_reqs is a set?

Sets do not provide stable scheduling order. Sorting by uid makes decode batches deterministic.

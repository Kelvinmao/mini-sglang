Prefill and KV Cache Allocation

Goal: predict how one tokenized prompt becomes a prefill batch with table rows, cache handles, token ids, and page-table entries.

The Win

After this lesson, you should be able to open prefill.py and cache.py and answer: "What is this request allowed to reuse, and what must be allocated before the engine runs?"

Primary sources: scheduler/prefill.py, scheduler/cache.py, and the scheduler/KV-cache map.

The Key Variable

The scheduler does not think only in "prompt length." It thinks in three lengths on Req:

cached_len

How many leading tokens already have usable KV-cache locations.

device_len

How many tokens are currently represented in device-side tables.

extend_len

The uncached region for the next model forward: device_len - cached_len.

If you remember one thing: cached_len separates reused KV-cache state from work that must be computed now.

The Admission Walk

  1. Scheduler._process_one_msg receives UserMsg and calls PrefillManager.add_one_req.
  2. PrefillManager.schedule_next_batch creates a PrefillAdder with a token budget and a reserved-size estimate for decode work already in flight.
  3. PrefillAdder._try_allocate_one calls CacheManager.match_req to find a reusable prefix.
  4. The returned cache handle gives cached_len. The uncached prompt work is input_len - cached_len.
  5. If capacity is available, the prefix handle is locked, a table row is allocated, and matched prefix token ids plus matched physical KV-cache locations are copied into that row.
  6. PrefillAdder._add_one_req copies the next uncached prompt slice into the token pool and returns either Req or ChunkedReq.

Why Chunking Exists

A long prompt may exceed the current prefill token budget. In that case, _add_one_req returns ChunkedReq. A chunked request is a real forward input, but it must not sample or enter decode yet.

The next scheduler iteration continues the same pending request from the chunk's table_idx, cache_handle, and cached_len.

Where Pages Are Allocated

Prefill admission reserves logical ownership, but Scheduler._prepare_batch is where page-table preparation happens. It calls: 

self.cache_manager.allocate_paged(batch.reqs)

Inside allocate_paged, each request computes: 

first_page = ceil(cached_len / page_size)
last_page = ceil(device_len / page_size)

Pages in the half-open range [first_page, last_page) intersect the uncached region. Those pages get fresh physical KV-cache slots, then _write_page_table writes token-level physical locations into the engine's page table.

Mental Simulation

Suppose page_size = 4, prompt length is 10, and the radix cache matched 6 prefix tokens. At admission: 

cached_len = 6
device_len = 10
extend_len = 4

Allocation uses ceil(6 / 4) = 2 and ceil(10 / 4) = 3, so it allocates one new page. That page covers token positions 8..11, even though only positions 8 and 9 are used immediately. Page allocation is page-granular; attention reads token-level page-table entries.

Modification Map

Change who gets admitted

Edit PrefillManager.schedule_next_batch or PrefillAdder.try_add_one.

Change capacity estimates

Edit PrefillAdder._try_allocate_one and compare against DecodeManager.inflight_tokens.

Change page allocation

Edit CacheManager.allocate_paged, _allocate, or _page_to_token.

Change prefix reuse

Edit RadixPrefixCache.match_prefix, insert_prefix, or evict.

Retrieval Check 1

A prompt has 20 tokens, and the prefix cache matched 12. What is extend_len for the initial complete prefill request?

extend_len is 8, because device_len starts at 20 and cached_len is 12.

Retrieval Check 2

With page_size = 8, cached_len = 9, and device_len = 17, how many fresh pages does allocate_paged request?

One page. ceil(9 / 8) = 2 and ceil(17 / 8) = 3, and the allocation range is [first_page, last_page), so the count is 3 - 2 = 1.

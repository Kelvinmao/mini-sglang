Visualize the Scheduler and KV-Cache

Goal: watch the batch, the radix prefix tree, and page memory change step by step, so prefill, decode, prefix reuse, and eviction stop being abstract.

The Win

The scheduler and radix cache are the hardest parts to picture from source alone. This tool records what actually happened during a run and lets you scrub through it, one scheduler iteration at a time.

Primary sources: trace/tracer.py, benchmark/offline/trace_radix_demo.py, visualizer/index.html, and the visualizer map.

First Principle

Recording is decoupled from viewing. The engine only appends a cheap snapshot per step; the browser does all the drawing. When tracing is off, every hook is a single boolean check, so the hot loop is unaffected.

Tracing runs with overlap scheduling disabled so each recorded step is exactly one schedule → forward → commit unit.

Generate a Trace

python benchmark/offline/trace_radix_demo.py

This writes visualizer/sample-trace.json. The scenario is built from explicit token ids: two prompts share a long prefix (reuse), several long distinct prompts create pressure (chunked prefill), and a small page budget forces eviction.

No working GPU (e.g. Turing / RTX 20-series, where the attention kernels will not run)? Use the pure-Python generator instead — it reimplements the radix-cache algorithm and needs no GPU, no CUDA, and no PyTorch: 

python visualizer/gen_trace.py

Open the Viewer

cd visualizer && python -m http.server 8123
# then open http://localhost:8123/ in a browser

Serving over HTTP lets the page load the checked-in sample automatically. You can also open index.html directly and drag any trace.json onto the page.

What Each Panel Shows

Radix tree

Each node is one compressed edge; the number is its token-span length. Blue = protected by a live request, amber = evictable. A gold ring marks the node a request just matched.

Batch composition

One row per request in the step, tagged prefill/decode/chunked. The blue portion is the cached prefix; the green portion is the tokens this step computed.

Memory & pages

The stacked bar splits capacity into protected, evictable, in-use, and free. The sparkline tracks free pages across the whole run.

Scrubber

Play, step, or drag; arrow keys step, space toggles play. The caption summarizes what changed.

Exercise

  1. Find the step where the second prompt reuses the shared prefix. How many tokens did it skip computing?
  2. Find the first eviction. Which node disappeared, and what freed it?
  3. Re-run with --num-pages larger. Does eviction still happen? Confirm your prediction against the source in kvcache/radix_cache.py.

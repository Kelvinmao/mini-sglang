Goal: build the first mental model you need before running Mini-SGLang or changing scheduler/KV-cache code.

The One-Sentence Model

Mini-SGLang is a set of cooperating processes: the API server accepts text, tokenizer workers turn text into token ids, scheduler workers choose prefill/decode batches, the engine runs the model and samples tokens, and the detokenizer streams text back.

Primary source: docs/structures.md. Keep the glossary open while reading source.

The File Trail

1. Start processes

server/launch.py starts one scheduler per tensor-parallel rank, tokenizer workers, and one detokenizer worker.

2. Accept HTTP

server/api_server.py handles /generate and /v1/chat/completions, assigns a request id, and sends a TokenizeMsg.

3. Tokenize

tokenizer/tokenize.py converts text to token ids. The worker in tokenizer/server.py wraps those ids into UserMsg.

4. Schedule

scheduler/scheduler.py receives UserMsg, asks prefill/decode managers for the next batch, prepares tensors, and calls the engine.

5. Execute

engine/engine.py runs model forward, samples next tokens, and returns GPU and CPU token copies.

6. Stream text

tokenizer/detokenize.py turns generated token ids into incremental printable text.

The Scheduler Core

Scheduler modification work usually starts with three questions:

  1. Should this request enter prefill now?
  2. Which decode requests should run this iteration?
  3. Which KV-cache pages and page-table entries must exist before the engine runs?

In this repo, those questions map to prefill.py, decode.py, and cache.py.

Prefill vs Decode

Prefill processes the prompt region that is not already cached. It may handle many prompt tokens for a request. Decode processes one newly generated token per running request and repeats until stop conditions are met.

In Req, cached_len means "tokens already backed by KV cache." device_len means "tokens currently represented in scheduler-owned device tables." The next forward processes device_len - cached_len tokens.

Run Checklist

To run the real server, you need Linux, CUDA-capable NVIDIA hardware, compatible CUDA tooling, and the package installed from this repo. The repo's quick-start command is: 

python -m minisgl --model "Qwen/Qwen3-0.6B"

For a first code-reading session, do not start by tuning performance. Start by confirming which processes launch and which endpoint you are using: /generate or /v1/chat/completions.

Retrieval Check

Without looking back, answer: a request has just been tokenized. Which object carries it into the scheduler, and which manager sees it first?

The tokenizer worker sends a UserMsg. The scheduler receives it in _process_one_msg and adds it to PrefillManager with add_one_req.

Source Exercise

Open core.py and find Req.extend_len. Then open scheduler/cache.py and find the loop in allocate_paged. Explain why allocation starts from cached_len, not from zero.

Tokens before cached_len already have usable KV-cache locations, either from a matched prefix or prior work. The scheduler only needs fresh pages for the uncached region [cached_len, device_len).

Should We Add More Inline Comments?

Goal: decide when comments help you learn and maintain Mini-SGLang, and when they make the source harder to trust.

Short Answer

Add more comments selectively, not everywhere. Mini-SGLang benefits from comments around scheduler/cache invariants, async CUDA behavior, page-table ownership, radix-cache locking, and non-obvious performance tradeoffs. It does not benefit from line-by-line tutorial comments.

Reference: the commenting policy.

The Rule

A good production comment answers one of these questions:

  1. Why is this code shaped this way?
  2. What invariant must future changes preserve?
  3. What external constraint is not visible in the local code?

If a comment only says what the next line does, it is usually noise.

Good Targets In This Repo

Scheduler/cache boundary

Comments help around cached_len, device_len, page-table writes, and free-list ownership.

Radix cache

Comments help around page-aligned matching, handle locking, ref-count accounting, and LRU leaf eviction.

Overlap scheduling

Comments help explain which work happens on which stream and why result processing is delayed.

Mac/MPS adaptation

Comments should identify CUDA-only assumptions before replacing them with backend abstractions.

Bad Comment

# Sort the requests by uid.
return Batch(reqs=sorted(self.running_reqs, key=lambda req: req.uid), phase="decode")

This repeats the code.

Better Comment

# running_reqs is a set, so sort before batching to keep scheduling deterministic.
return Batch(reqs=sorted(self.running_reqs, key=lambda req: req.uid), phase="decode")

This explains the invariant: deterministic scheduling despite set storage.

Where Long Explanations Belong

Put broad explanations in lessons, references, design docs, or tests. Put short constraints in code. For example, a full explanation of radix cache belongs in lesson 0003; source comments should only guard the specific invariant near the code that depends on it.

Retrieval Check

Should a comment explain what req.can_decode returns, or why finished requests must be removed before another decode batch?

Prefer the second. The property name already says what it returns; the useful comment explains the scheduling invariant.

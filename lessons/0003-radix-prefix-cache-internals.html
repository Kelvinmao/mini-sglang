Radix Prefix Cache Internals

Goal: understand how Mini-SGLang remembers reusable prefixes without confusing logical token prefixes with physical KV-cache memory.

The Win

After this lesson, you should be able to read radix_cache.py and explain what happens during match_prefix, insert_prefix, lock_handle, and evict.

Primary sources: kvcache/radix_cache.py, kvcache/base.py, and the radix prefix cache reference.

Separate Two Things

The radix cache is not the KV tensor storage. It is an index. It maps logical token prefixes to physical KV-cache token locations that were already allocated by the scheduler cache manager.

Logical side

Token ids in RadixTreeNode._key. These describe which prompt prefix is reusable.

Physical side

KV-cache token locations in RadixTreeNode._value. These point attention kernels at existing K/V data.

Compressed Edges

A node stores one edge segment, not necessarily one token. If the tree has an edge for tokens [10, 11, 12, 13], the node stores those four token ids and the four matching physical KV locations.

The full prefix for a handle is rebuilt by walking from the handle's node up to the root and concatenating each node's value. That is what RadixCacheHandle.get_matched_indices does.

How Matching Works

  1. match_prefix calls _tree_walk(input_ids).
  2. _tree_walk uses the first token, or first page of tokens, to choose a child.
  3. The child edge is compared to the remaining input with fast_compare_key.
  4. The match length is aligned down to page_size, because KV memory is allocated and evicted by page.
  5. If only part of an edge matches, split_at creates a new parent edge for the shared prefix and leaves the old suffix beneath it.

Why Handles Must Be Locked

A matched handle points to reusable physical KV-cache locations. If those locations are evicted before the scheduler copies them into a live request row, the request would point at freed memory.

lock_handle increments reference counts along the matched path. When a node's count moves from zero to one, its token slots move from evictable_size to protected_size.

Unlocking reverses the accounting. When a node's count reaches zero, it can be evicted again.

How Insertion Works

insert_prefix(input_ids, indices) first aligns the insert length down to page_size. Then it walks the existing tree. If the full prefix is already present, it returns a handle to the existing node. If not, it appends one new node containing only the missing suffix. 

insert_len = align_down(len(input_ids), page_size)
node, prefix_len = _tree_walk(input_ids[:insert_len])
if prefix_len != insert_len:
    add one new suffix node

How Eviction Works

Eviction only removes unprotected leaves. It collects leaf nodes with ref_count == 0, heaps them by timestamp, and removes the oldest leaves until it has freed enough token slots.

It returns physical token indices, not page starts. That is why scheduler/cache.py uses evicted[:: self.page_size] before putting evicted memory back into free_slots.

Mental Simulation

Assume page_size = 2. The cache contains a prefix edge for tokens [1, 2, 3, 4]. A new prompt starts with [1, 2, 9, 9].

The raw common prefix is two tokens. Since two is already page-aligned, _tree_walk splits the old edge at position two. The tree now has shared edge [1, 2], and the old suffix [3, 4] hangs under it.

The new request can reuse exactly two tokens of KV cache. Its cached_len is two.

Retrieval Check 1

In this repo, does the radix cache own the K/V tensors themselves, or does it index physical locations owned elsewhere?

It indexes physical locations owned elsewhere. The engine owns the KV tensors, while the scheduler cache manager and radix cache track which physical slots can be reused.

Retrieval Check 2

Why does _tree_walk align the match length down to page_size?

Because KV-cache allocation and eviction are page-granular. Reusing a partial page would break the scheduler's page-table and free-list assumptions.

Source Exercise

Open radix_cache.py. Find the line in evict that rejects protected nodes, then find the line in lock_handle that moves a node from evictable to protected.

evict asserts node.ref_count == 0 before removing a leaf. lock_handle moves accounting when a node's ref_count is zero before incrementing it.

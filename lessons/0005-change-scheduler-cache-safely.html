Change Scheduler and Cache Code Safely

Goal: learn a practical edit loop for scheduler and KV-cache changes: identify the invariant, test the smallest owner, then broaden validation.

The Win

You want to modify scheduler/KV-cache logic. The risk is trying to validate every idea by launching a full model server. Instead, most scheduler and cache changes should start with a narrow invariant test.

Primary sources: tests/core/test_cache_allocate.py, scheduler/decode.py, scheduler/cache.py, and the workflow reference.

The Edit Loop

  1. Say the behavior change in one sentence.
  2. Map it to the smallest owner file.
  3. State the invariant that must stay true.
  4. Write a targeted test at that owner boundary.
  5. Make the smallest implementation change.
  6. Run the targeted test before broad GPU/server validation.

For scheduler/cache work, a good invariant test usually beats a full server run as the first feedback loop.

Pick The Owner

Admission policy

Owner: prefill.py. Ask: which pending request enters prefill, and how much prompt work can it do now?

Decode policy

Owner: decode.py. Ask: which running requests form the next decode batch?

Prefill/decode priority

Owner: scheduler.py. Ask: does the next iteration choose prefill first, decode first, or a mix?

KV page allocation

Owner: cache.py. Ask: which physical pages are allocated, freed, evicted, or written into the page table?

Radix prefix reuse

Owner: radix_cache.py. Ask: what prefix matched, what was inserted, and what is evictable?

Request invariants

Owner: core.py. Ask: how do cached_len, device_len, and remain_len change?

Example 1: Decode Policy

Suppose you want decode batches to stay deterministic. The invariant is: decode batches are sorted by request id. The owner is DecodeManager.schedule_next_batch. 

def test_decode_batch_sorted_by_uid():
    dm = DecodeManager(page_size=4)
    req3 = make_req(uid=3)
    req1 = make_req(uid=1)

    dm.filter_reqs([req3, req1])

    batch = dm.schedule_next_batch()
    assert [req.uid for req in batch.reqs] == [1, 3]

This test does not need model weights, a tokenizer, CUDA graphs, or an API server. It tests the policy owner directly.

Example 2: Cache Allocation

The existing test_cache_allocate.py is the pattern to copy. It creates a CPU CacheManager, inserts evictable prefixes, exhausts free pages, and checks page alignment after eviction.

The invariant is not "the server still runs." It is sharper: after eviction, allocated pages and remaining free slots are page-aligned and non-overlapping. 

allocated = cm._allocate(2)
assert len(allocated) == 2
assert_all_page_aligned(allocated, page_size)
assert_no_overlap(allocated, page_size)

Testing Ladder

  1. Pure policy test: DecodeManager, TableManager, helper functions.
  2. CPU cache test: CacheManager, radix insertion, eviction, page alignment.
  3. Scheduler integration test: message flow, queues, prefill/decode interaction.
  4. GPU kernel test: custom CUDA/Triton behavior.
  5. Full server smoke test: model load, process wiring, API request, streaming response.

Climb only as high as the change requires. A radix tree split bug should usually fail before the full server layer.

Source Exercise

Open test_cache_allocate.py and find _make_cache_manager. Then open core.py and find why that helper must set a global Context before creating a radix cache.

RadixPrefixCache reads get_global_ctx().page_size. The test helper creates Context(page_size=...) and calls set_global_ctx so radix-cache page alignment matches the test case.
